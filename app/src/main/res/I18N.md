# Android translations

`values/strings.xml` is the base (English) table. Every screen, dialog, notification and layout
string resolves through `R.string.*`, so a locale directory such as `values-es/strings.xml`
overrides any subset of them and Android falls back to English for the rest.

## Adding or completing a language

For one Android and web translator workbook, use the monorepo's `scripts/i18n-sheet.py` via
`make i18n-sheet-export LANG=es OUT=chronicle-es.xlsx`, have a human fill the `spanish` column,
then run `make i18n-sheet-import LANG=es IN=chronicle-es.xlsx`. Keep the English cells and
placeholders unchanged; incomplete Android arrays and plurals are omitted with a warning.

1. Create `values-<lang>/strings.xml` containing only the `<string>`/`<plurals>` entries you
   translate. Keep `%1$s`-style placeholders and `\n` line breaks verbatim.
2. A flavor or build type with its own English (`src/research/res/values`, `src/amazon/res/values`,
   `src/debug/res/values`) needs the translation in its own `values-<lang>` folder. Android's merge
   otherwise shows main's translation of main's English, which lint does not report;
   `make i18n-source-check LANG=<lang>` lists these as `shadowed`.
3. Lint (`./gradlew :app:lintOpenDebug`) reports `MissingTranslation` for keys still missing.
   Every flavor bundles every locale.
4. Do not machine-translate; only a qualified translator should fill a table.

## Per-module consent copy

The participant-facing consent templates (label, "what it collects", "what it does NOT collect",
privacy class, caveats) exist only as resources: `values/consent_copy.xml` (modules every artifact
supports) and `../googleServices/res/values/consent_copy.xml` (restricted modules, research and
open only). `CollectionConsentCopy.kt` maps each module id to its typed resource ids; the
restricted modules' map is in the googleServices `DistributionCollectionContributions.kt`.

| Resource | Type |
| --- | --- |
| `consent_<module_id>_label` | string |
| `consent_<module_id>_privacy_class` | string |
| `consent_<module_id>_collects` | string-array |
| `consent_<module_id>_not_collects` | string-array |
| `consent_<module_id>_collects_<n>`, `consent_<module_id>_not_collects_<n>` | string (individual bullet; identical bullets share a key) |
| `consent_health_connect_caveats` | string-array |
| `consent_health_connect_collects_trailer` | string (bullet after the study-approved record types, which come from `hc_record_<type>`) |
| `consent_sensor_privacy_class`, `consent_sensor_not_collects` | shared by every `sensor_*` module, which has only `_label` and `_collects` |

Put only translated string keys in `values-<locale>/consent_copy.xml`. Shared-module arrays reference
individual strings: leave those arrays unchanged so each missing translation falls back to its
English string. Restricted-module inline arrays still need a complete translated array. A new module
needs its keys in the right file and an entry in the matching map.

## Still English-only

- Pure presenters (`activeEnrollmentSummary`, `renderUploadHistory`, `formatDailyUploadStats`,
  `notificationAccessDisclosure`, `CollectionCapabilityResolver`, `sensorCollectionStatusText`,
  `StudyDisclosureCopy.Labels`) keep a JVM-tested English table as their
  default `CopyResolver`/labels object; every screen passes `requireContext().copyResolver()`
  (or the `fromResources(context)` variant) so the same code follows the device locale.
- Strings the server sends (study title, policy text, reminder titles) follow the study, not the
  device locale.
- Device-user choices: `user_study_participant_label`, `user_someone_else_label` and `user_unassigned_label`
  are display text only and translate normally. The value written to `current_user` and the user
  queue, uploaded and exported, is `DeviceUser.stored` (English "Study participant" / "Someone else" / "Not set"), never a resource string.
  Older releases wrote "Target child" / "Other"; `DeviceUser.fromStored` maps them on every read.
- Uploaded telemetry values are never translated: `usageInteractionType` labels,
  `DeviceLifecycleEvents` constants,
  `ModuleResult` reasons/`redactedMessage`, module ids, and all `Log`/`require`/`check` text.

## Verifying nothing is hardcoded

- Layout/menu XML: Android lint's `HardcodedText` is promoted to an error in `app/lint.xml`, so
  `./gradlew :app:lintOpenDebug` fails on a literal `android:text`, `hint`, or
  `contentDescription`.
- Kotlin: `ast-grep scan app/src/main collection-*/src/main` (rule `android-i18n-ui-literal` in
  `lint/i18n/`, also run by the monorepo `make i18n-lint`) fails on a literal string, or
  `"literal" + expr`, reaching `Toast.makeText`, `Snackbar.make`, dialog and notification builder
  setters, `NotificationChannel`, `setText`/`setHint`/`setContentDescription`/`setSummary`, and
  the `text`/`hint`/`title`/`subtitle`/`contentDescription`/`summary`/`error` properties. It
  matches by node shape, so comments and line breaks inside a builder chain do not hide a setter,
  and a chain is reported on the line where it starts, once per setter.
- Suppress a deliberate wire value with `// ast-grep-ignore: android-i18n-ui-literal` (or a bare
  `// ast-grep-ignore`) on its own line directly above the statement, or as a trailing comment on
  the same line. A `-- reason` after the rule id is allowed (ast-grep >= 0.45.2, enforced by
  `scripts/i18n-lint.sh`).
- Proof: `lint/i18n/cases/` is a table-driven suite (`FIRE: rule-id` markers must produce exactly
  those findings; ignored `src/test`/`src/androidTest` paths and every suppression form are
  exercised). The monorepo `scripts/i18n-lint-cases.py` runs it from `scripts/i18n-lint.sh`;
  `scripts/i18n-lint-mutation.sh` also plants a violation under `app/src/main`, checks the scan
  fails naming it, and removes it.
- Known holes, on purpose: a template with no literal words (`"$label: 42"`), a literal chosen by
  an `if/else` expression, `Log`/`require`/`check` text, and bare `text = "…"` without a receiver.

Verified with ast-grep 0.42.1.

**Built-in checks.** `app/lint.xml` also promotes Android Lint's `SetTextI18n` to an error, so a
literal or `"$a" + b` concatenation passed to `TextView.setText` fails the build; join localized
pieces with a format resource (`ds_module_row` = `%1$s\n%2$s`) instead. The ast-grep rules cover
the sinks Lint does not (Toast, Snackbar, notifications, dialogs, property assignment).

**Pseudolocales.** Debug builds set `pseudoLocalesEnabled true`. On a device, Settings >
Developer options > Languages, or `adb shell settings put system system_locales en-XA`, renders
every resource string accented (`en-XA`) or mirrored (`ar-XB`); anything still plain English on
screen is hardcoded. A custom Android Lint UAST detector was the alternative to
ast-grep for Kotlin and was not chosen because it needs its own Gradle module and test rig for
the same result.
